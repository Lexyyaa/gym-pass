## 1. 요구사항 분류

### 1.1 기능 요구사항

1. 회원 등록: 이름, 연락처를 받는다 (S-16)
2. 회원권 등록: 회원 · 종류 · 시작일 · 기간(개월) 또는 횟수 · 결제 금액을 받는다 (S-17)
3. 한 회원은 같은 시점에 유효한 회원권을 하나만 가진다 (S-18)
4. 회원권 종류를 추후 추가할 수 있는 구조여야 한다 (S-19)
5. 회원 출입을 기록한다 (S-20)
6. 유효한 회원권이 있어야 출입할 수 있다 (S-21)
7. 횟수제는 출입 시 1회 차감한다 (S-22)
8. 하루 여러 번 출입해도 횟수는 하루 1회만 차감한다 (S-23)
9. 회원권을 일정 기간 정지할 수 있다 (S-24)
10. 정지 기간만큼 종료일이 연장된다 (S-25)
11. 정지 횟수와 기간에 상한을 둔다 (S-26 · S-27)
12. 정지 중에는 출입할 수 없다 (S-28)
13. 만료 7일 전과 당일에 안내 메시지를 발송한다 (S-29)
14. 횟수제는 잔여 3회일 때 안내한다 (S-30)
15. 안내는 매일 09:00에 자동 실행한다 (S-31)
16. 발송 실패 건은 상한까지 재시도한다 (S-32 · S-33)
17. 지점의 회원권 목록을 상태별 필터 · 만료 임박 순 정렬로 조회한다 (S-34 · S-35)
18. 회원 한 명의 출입 이력과 회원권 변경 이력을 조회한다 (S-36)
19. 요청 헤더로 지점을 식별하고, 다른 지점 데이터 접근은 거부한다 (S-10)
20. MessageClient 가짜 구현체를 작성한다 (S-13 · S-15)

### 1.2 비기능 요구사항

**성능**
1. 지점 200곳 · 회원 10만 명 규모를 전제한다 (S-4)
2. 회원권 목록 조회 쿼리의 실행 계획과 인덱스 설계 근거를 제시한다 (S-40)
3. 외부 발송은 100~500ms 지연을 전제로 처리 흐름을 설계한다 (S-14)

**정합성**
1. 같은 회원의 동시 출입 요청에서도 하루 1회 차감이 지켜져야 한다 (S-23 · S-37)
2. 유효 회원권 1개 제약이 동시 요청에서도 지켜져야 한다 (S-18)
3. 다른 지점 데이터에 접근할 수 없어야 한다 (S-10)
4. 정지·연장 날짜 계산이 월말 · 2월에서도 정확해야 한다 (S-38)
5. 만료 안내 대상 선정이 경계일에서 정확해야 한다 (S-39)

**가용성**
1. 원문에 없음

**운영성**
1. Docker Compose로 실행 가능해야 한다 (S-8)
2. 가짜 구현체의 지연·실패 비율을 설정값으로 조절할 수 있어야 한다 (S-15)
3. 만료 안내가 매일 09:00에 자동 실행되어야 한다 (S-31)
4. 발송 실패 건을 재시도하고 상한을 관리한다 (S-32 · S-33)
5. 가정과 근거 · 검증 결과 · AI 활용 내역을 README에 기재한다 (S-12 · S-42)

**확장성**
1. 회원권 종류가 추후 추가될 수 있어야 한다 (S-19)
2. 지점 200곳 · 회원 10만 명 규모에서 동작해야 한다 (S-4)

## 2. 문장별 심문

### S-1

> 백엔드 과제: 헬스장 회원권 관리

- 심문 대상 아님: 제목이다

### S-2

> 헬스장 운영자가 회원과 회원권을 관리하고, 회원의 출입을 기록하며, 회원권 만료 전 안내를 발송하는 서비스의 백엔드를 구현합니다.

- 심문 대상 아님: 배경 설명이다. 구체 규칙은 필수 요구사항 절에서 심문한다

### S-3

> 제한 시간 3시간, AI 도구 사용 자유

- 심문 대상 아님: 진행 조건 안내다

### S-4

> 지점 200곳, 회원 10만 명 규모

- 명시되지 않은 것
  - 회원권 · 출입 기록의 건수 규모 (회원 10만 명 × 일 출입이면 연간 수천만 건)
  - 지점당 동시 요청량 · 처리량 목표치
  - 회원이 지점에 소속되는지, 여러 지점을 오갈 수 있는지
- 깨지는 시나리오
  - 출입 기록이 누적되면서 목록 · 이력 조회가 풀 스캔으로 느려진다
  - 회원-지점 관계를 정하지 않으면 지점 격리(S-10)의 기준 자체가 없다
- 어긋나는 데이터
  - 인덱스 없는 조회가 타임아웃되어 목록 · 이력이 응답 불능이 된다
  - 회원이 어느 지점 소속인지 판단할 수 없어 다른 지점의 회원 데이터가 노출된다

### S-5

> 필수 요구사항을 모두 구현하기 어려울 수 있습니다.

- 심문 대상 아님: 진행 안내다

### S-6

> 구현 범위와 우선순위도 평가에 포함됩니다.

- 심문 대상 아님: 평가 안내다. §5에서 다룬다

### S-7

> Java 17 이상, Spring Boot 3.x, Spring Data JPA, MySQL

- 명시되지 않은 것
  - MySQL 버전 (8.x인지, 격리 수준 기본값 전제)
- 깨지는 시나리오
  - 로컬과 Docker의 MySQL 버전이 다르면 날짜 함수 · 인덱스 동작이 달라 검증 결과가 어긋난다
- 어긋나는 데이터
  - 실행 계획(S-40) 증빙이 제출 환경에서 재현되지 않는다

### S-8

> Docker Compose로 실행 가능

- 명시되지 않은 것
  - 앱까지 포함해 올리는지, DB만 올리고 앱은 로컬 실행인지
  - 초기 데이터(seed) 투입 방식
- 깨지는 시나리오
  - 평가자가 clone 직후 실행했는데 DB 초기화 순서 문제로 앱이 기동 실패한다
- 어긋나는 데이터
  - 스키마 없는 DB에 앱이 붙어 기동 자체가 실패하고, 검증이 불가능해진다

### S-9

> 인증 미구현.

- 심문 대상 아님: 범위 제외 선언이다. 지점 식별 규칙은 S-10에서 심문한다

### S-10

> 요청 헤더로 지점을 식별하며 다른 지점 데이터 접근은 거부

- 명시되지 않은 것
  - 헤더 이름 · 값 형식 (숫자 ID인지 코드인지)
  - 헤더가 없거나 존재하지 않는 지점일 때의 응답 (400 · 401 · 404)
  - "거부"의 응답 코드 (403인지, 존재 은닉을 위한 404인지)
  - 어떤 데이터가 지점에 귀속되는지 (회원인지 회원권인지 출입 기록인지)
- 깨지는 시나리오
  - 특정 API에서만 지점 검증을 빼먹으면 헤더만 바꿔 타 지점 회원 이력을 조회할 수 있다
  - 회원이 지점 소속이 아니라면 "다른 지점 데이터"의 정의가 성립하지 않는다
- 어긋나는 데이터
  - A 지점 운영자가 B 지점 회원의 연락처 · 이력을 열람한다 (정보 유출)
  - 타 지점 회원권에 정지 · 출입 처리가 들어가 소유 지점의 데이터가 오염된다

### S-11

> REST API로 설계하고 API 명세를 README 또는 별도 문서에 기재

- 심문 대상 아님: 제출물 형식 안내다

### S-12

> 요구사항 중 정의가 필요한 부분은 직접 가정하고 README에 근거를 기재

- 심문 대상 아님: 진행 방식 안내다. 가정할 항목 자체는 §4에 모은다

### S-13

> `public interface MessageClient { SendResult send(String phone, String text); }`

- 명시되지 않은 것
  - `SendResult`의 구조 (성공/실패 구분 방식, 실패 사유 포함 여부)
  - 실패가 반환값인지 예외인지
  - 동기 호출만 있는지 (비동기 콜백 없음)
- 깨지는 시나리오
  - 실패를 예외로만 처리하면 실패 응답(SendResult로 반환) 케이스를 놓쳐 재시도 대상에서 누락된다
- 어긋나는 데이터
  - 실패 건이 성공으로 기록되어 재시도(S-32)가 일어나지 않는다

### S-14

> 응답 지연 100~500ms, 일부 요청은 실패 응답

- 명시되지 않은 것
  - "일부"의 기본 실패 비율
  - 지연 상한 500ms를 넘는 타임아웃 케이스 존재 여부
  - 실패가 일시적(재시도하면 성공 가능)인지 영구적인지
- 깨지는 시나리오
  - 대상 수천 건을 직렬 발송하면 건당 최대 500ms × 건수만큼 배치가 길어져 다음 실행(다음 날 09:00)과 겹칠 수 있다
- 어긋나는 데이터
  - 밀린 배치가 겹쳐 실행되면 같은 회원권에 안내가 이중 발송된다

### S-15

> 가짜 구현체를 작성하고 지연·실패 비율을 설정값으로 조절 가능해야 함

- 명시되지 않은 것
  - 설정 형식 (application.yml 프로퍼티인지 환경 변수인지)
  - 실패 비율 0% · 100% 같은 극단값 지원 여부 (테스트에서 결정적 동작 필요)
- 깨지는 시나리오
  - 실패가 랜덤이면 재시도 테스트가 비결정적으로 성공/실패를 오간다
- 어긋나는 데이터
  - 검증 결과(S-42)가 실행할 때마다 달라져 재현 불가능한 증빙이 된다

### S-16

> 회원 등록: 이름, 연락처

- 명시되지 않은 것
  - 연락처 형식 · 검증 규칙 · 중복 허용 여부
  - 회원이 지점에 귀속되는지
  - 같은 등록 요청이 두 번 오면 회원이 둘 생기는지
- 깨지는 시나리오
  - 네트워크 재전송으로 같은 이름 · 연락처 등록이 두 번 처리된다
- 어긋나는 데이터
  - 동일 인물의 회원 레코드가 2건 생기고, 안내 메시지도 이중 발송된다

### S-17

> 회원권 등록: 회원, 종류(기간제 또는 횟수제), 시작일, 기간(개월) 또는 횟수, 결제 금액

- 명시되지 않은 것
  - 시작일이 과거 · 미래일 수 있는지
  - 기간(개월)의 종료일 계산 규칙 (1/31 + 1개월 = 2/28인지 3/2인지, 종료일 포함/미포함)
  - 횟수제에 유효기간이 있는지 (시작일만 받고 종료일이 없음)
  - 횟수 · 개월 · 금액의 최소/최대값 (0 · 음수 허용 여부)
- 깨지는 시나리오
  - 1/31 시작 1개월권의 종료일을 단순 일수 더하기로 계산하면 2월에서 날짜가 밀린다
  - 횟수제에 종료일이 없으면 "만료 임박 순 정렬"(S-35)과 "만료 7일 전 안내"(S-29)에 횟수제를 넣을 방법이 없다
- 어긋나는 데이터
  - 같은 조건의 회원권인데 등록 월에 따라 이용 일수가 달라진다
  - 횟수제 회원권이 만료 관련 조회 · 안내에서 통째로 누락되거나 정렬이 깨진다

### S-18

> 한 회원은 같은 시점에 유효한 회원권을 하나만 가질 수 있음

- 명시되지 않은 것
  - "유효한"의 정의 (정지 중 · 미래 시작 · 잔여 0회가 유효에 포함되는지)
  - 위반 시 응답 (거부인지, 기존 회원권 종료 후 대체인지)
  - 동시에 두 등록 요청이 오면 어떻게 막는지
- 깨지는 시나리오
  - 두 창구에서 같은 회원의 회원권을 동시에 등록하면 검사-삽입 사이 틈으로 둘 다 통과한다
  - 정지 중 회원권을 "유효 아님"으로 해석하면 정지 기간에 새 회원권 등록이 허용되어 해제 시 2개가 겹친다
- 어긋나는 데이터
  - 한 회원에게 유효 회원권 2건이 생겨 출입 차감 · 안내 대상 선정이 어느 쪽 기준인지 결정 불능이 된다

### S-19

> 회원권 종류는 추후 추가 예정

- 명시되지 않은 것
  - 추가될 종류의 성격 (기간+횟수 혼합형 등) 예시 없음
  - "추가 가능"의 요구 수준 (코드 수정 없이인지, 확장 지점만 마련하면 되는지)
- 깨지는 시나리오
  - 종류를 if-else 분기로 박아두면 새 종류 추가 때 출입 · 안내 · 조회 로직 전부를 고쳐야 한다
- 어긋나는 데이터
  - 새 종류 추가 시 기존 종류의 차감 · 만료 판정 로직이 회귀 오류를 일으킨다

### S-20

> 회원 출입 기록.

- 명시되지 않은 것
  - 기록 항목 (일시 · 지점 · 회원권 스냅샷 포함 여부)
  - 출입 시각을 서버가 찍는지 클라이언트가 보내는지
  - 거부된 출입 시도도 기록하는지
- 깨지는 시나리오
  - 클라이언트 시각을 믿으면 조작된 날짜로 "어제" 출입을 만들어 오늘 차감을 피할 수 있다
- 어긋나는 데이터
  - 출입 이력(S-36)의 시각이 실제와 어긋나고 하루 1회 판정(S-23)이 무력화된다

### S-21

> 유효한 회원권이 있어야 출입 가능

- 명시되지 않은 것
  - 유효 판정 시점 (요청 처리 시각 기준)
  - 시작일 당일 · 종료일 당일이 유효에 포함되는지
  - 잔여 0회 횟수제의 유효 여부
  - 거부 시 응답 코드와 사유 전달 방식
- 깨지는 시나리오
  - 종료일 당일 23:59 출입과 자정 직후 출입에서 포함/미포함 규칙이 없으면 지점마다 판정이 달라진다
- 어긋나는 데이터
  - 만료된 회원권으로 출입이 기록되거나, 유효한 마지막 날 출입이 거부된 이력이 남는다

### S-22

> 횟수제는 출입 시 1회 차감

- 명시되지 않은 것
  - 차감과 출입 기록이 한 트랜잭션인지
  - 잔여 1회에서 출입하면 그 출입은 허용되는지 (차감 후 0회)
  - 차감 내역이 회원권 변경 이력(S-36)에 남는지
- 깨지는 시나리오
  - 출입 기록은 남았는데 차감이 실패(또는 그 반대)하면 잔여 횟수와 이력이 어긋난다
- 어긋나는 데이터
  - 출입 이력 건수와 차감 횟수의 합계가 맞지 않아 잔여 3회 안내(S-30) 시점이 틀어진다

### S-23

> 같은 회원이 하루에 여러 번 출입해도 횟수는 하루 1회만 차감

- 명시되지 않은 것
  - "하루"의 기준 (달력일 자정 경계인지, 타임존)
  - 두 번째 이후 출입도 기록은 남기는지 (차감만 생략)
  - 여러 지점을 하루에 오가면 지점별로 각각 1회인지 전체 1회인지
- 깨지는 시나리오
  - 같은 회원의 출입 요청 2건이 동시에 들어오면 "오늘 차감했는가" 검사 시점이 겹쳐 둘 다 차감한다 (S-37이 이 시나리오를 명시)
  - 23:59와 00:01 출입을 같은 방문으로 볼지 규칙이 없으면 자정 직전 방문이 2회 차감된다
- 어긋나는 데이터
  - 잔여 횟수가 실제 이용일수보다 많이 깎여 회원 불만 · 정산 분쟁의 근거 데이터가 된다

### S-24

> 회원이 회원권을 일정 기간 정지할 수 있음.

- 명시되지 않은 것
  - 정지 요청 파라미터 (시작일+일수인지 시작/종료일인지)
  - 미래 예약 정지 · 소급 정지 허용 여부
  - 정지 조기 해제 · 취소 가능 여부
  - 기간제만 대상인지 횟수제도 정지 가능한지 (횟수제는 연장할 종료일이 없을 수 있음)
- 깨지는 시나리오
  - 이미 만료된 회원권에 정지 요청이 오면 종료일 연장으로 만료를 되살릴 수 있다
  - 정지 기간이 겹치게 두 번 요청하면 연장이 이중 계산된다
- 어긋나는 데이터
  - 종료일이 실제 미이용 기간보다 길게 늘어나 만료 안내 · 목록 정렬이 전부 밀린다

### S-25

> 정지 기간만큼 종료일이 연장됨

- 명시되지 않은 것
  - 연장 시점 (정지 등록 즉시인지, 정지 종료 확정 후인지)
  - "기간"의 단위와 경계 (정지 시작일 · 종료일 포함 여부, 일수 계산 방식)
  - 정지 중 조기 해제하면 실제 정지 일수만 연장하는지
- 깨지는 시나리오
  - 등록 즉시 연장했는데 조기 해제를 허용하면 안 쉰 기간만큼 종료일이 부풀려진 채 남는다
  - 월말 걸친 정지(예: 2/25~3/5)에서 일수 계산 규칙이 없으면 구현마다 종료일이 1~2일씩 다르다 (S-38이 이 지점을 검증)
- 어긋나는 데이터
  - 종료일과 실제 정지 일수의 합이 맞지 않아 날짜 계산 테스트(S-38)와 만료 안내 대상(S-39)이 어긋난다

### S-26

> 정지 가능 횟수와 기간에는 상한이 있음.

- 명시되지 않은 것
  - 상한의 적용 범위 (회원권당인지 연간인지)
  - 횟수 상한과 기간 상한이 각각인지 (1회 최대 일수 · 누적 최대 일수)
- 깨지는 시나리오
  - 1일짜리 정지를 반복해 누적 상한 검사를 피하는 요청이 들어온다
- 어긋나는 데이터
  - 사실상 무기한 정지가 가능해져 종료일이 무한정 밀린 회원권이 남는다

### S-27

> 상한은 직접 정의

- 심문 대상 아님: 가정을 위임하는 안내다. 수치는 C-2에서 결정한다

### S-28

> 정지 중에는 출입 불가

- 명시되지 않은 것
  - 정지 시작일 당일 · 종료일 당일의 출입 가능 여부
  - 거부 응답에 정지 상태임을 알려주는지
- 깨지는 시나리오
  - 정지 시작일 아침에 출입한 뒤 그날부터 정지가 적용되면 이용일이 정지 기간에 포함되어 이중 혜택이 된다
- 어긋나는 데이터
  - 정지 기간에 출입 기록이 남아 "정지 중 출입 불가"와 모순되는 이력이 생긴다

### S-29

> 회원권 만료 7일 전과 당일에 안내 메시지 발송

- 명시되지 않은 것
  - "7일 전"의 계산 기준 (종료일 - 7일이 오늘인 건만인지, 7일 이내 전부인지)
  - 이미 만료된(지난) 회원권은 대상 제외인지
  - 정지 중 회원권도 안내하는지 (정지로 종료일이 밀릴 수 있음)
  - 같은 회원권에 같은 안내가 두 번 가면 안 되는지
- 깨지는 시나리오
  - 7일 전 안내 발송 후 정지로 종료일이 밀리면, 새 종료일 기준으로 7일 전 안내를 다시 보내야 하는지 규칙이 없다
  - 배치가 하루 실패하면 "종료일-7일 == 오늘" 조건의 대상은 영영 안내를 못 받는다
- 어긋나는 데이터
  - 같은 회원이 같은 안내를 2번 받거나 0번 받는다 (발송 이력과 대상 선정 기준 불일치)

### S-30

> 횟수제는 잔여 3회일 때 안내

- 명시되지 않은 것
  - 정확히 3회일 때만인지, 3회 이하 전부인지
  - 트리거 시점 (차감으로 3회 도달한 순간인지, 다음 날 09:00 배치인지)
  - 3회에서 안내 후 잔여가 유지되면 매일 반복 발송하는지
  - 4회에서 하루 2회분 조정 등으로 2회가 되어 3회를 건너뛰면 안내를 하는지
- 깨지는 시나리오
  - "잔여 == 3" 조건이면 3을 건너뛴 회원권은 안내 대상에서 영영 빠진다
  - "잔여 <= 3" 조건이면 매일 09:00마다 같은 안내가 반복 발송된다
- 어긋나는 데이터
  - 안내를 못 받은 회원이 잔여 0회로 출입 거부를 당하거나, 같은 안내가 매일 쌓인다

### S-31

> 매일 09:00에 자동 실행

- 명시되지 않은 것
  - 타임존 (KST 전제인지)
  - 09:00에 서버가 죽어 있으면 놓친 실행을 보충하는지
  - 인스턴스가 2대면 배치가 2번 도는지 (중복 실행 방지)
  - 수동 재실행 수단이 필요한지
- 깨지는 시나리오
  - 배포가 09:00에 걸치면 그날 배치가 통째로 빠지거나, 재시작 전후로 2번 실행된다
- 어긋나는 데이터
  - 안내가 누락된 날이 생기거나, 같은 대상에 이중 발송된 이력이 남는다

### S-32

> 발송 실패 건은 재시도.

- 명시되지 않은 것
  - 재시도 시점 (즉시 N회인지, 다음 배치인지, 별도 주기인지)
  - 재시도 간격 · 백오프
  - 응답 지연 중 타임아웃 처리한 건의 성패 판정 (실제로는 발송됐을 수 있음)
  - 재시도 상한 도달 후의 처리 (포기 기록)
- 깨지는 시나리오
  - 타임아웃을 실패로 간주해 재시도하면 실제로는 이미 도착한 메시지가 한 번 더 간다
  - 재시도 처리 중 프로세스가 죽으면 어떤 건이 몇 번 시도됐는지 잃어버린다
- 어긋나는 데이터
  - 발송 시도 횟수 기록이 실제와 어긋나 상한 판정이 틀리고, 회원이 중복 메시지를 받는다

### S-33

> 상한은 직접 정의

- 심문 대상 아님: 가정을 위임하는 안내다. 수치는 C-3에서 결정한다

### S-34

> 지점의 회원권 목록.

- 명시되지 않은 것
  - 페이지네이션 여부와 방식 (10만 명 규모에서 전체 반환은 비현실적)
  - 응답에 포함할 필드 (회원 정보 포함 여부)
- 깨지는 시나리오
  - 페이지네이션 없이 대형 지점 목록을 조회하면 수만 건이 한 응답에 실린다
- 어긋나는 데이터
  - 응답 생성 중 메모리 · 타임아웃으로 조회 자체가 실패한다

### S-35

> 상태(유효, 정지, 만료)별 필터, 만료 임박 순 정렬

- 명시되지 않은 것
  - 상태가 저장 컬럼인지, 날짜 · 정지 여부에서 매번 계산하는 파생값인지
  - 세 상태가 전부인지 (미래 시작 대기 상태 · 잔여 0회 소진 상태의 소속)
  - 횟수제의 "만료 임박" 정렬 키 (종료일이 없으면 잔여 횟수로 대체하는지)
  - 필터 없이 전체 조회가 가능한지
- 깨지는 시나리오
  - 상태를 저장 컬럼으로 두면 자정에 만료된 회원권이 갱신 배치 전까지 "유효"로 조회된다
  - 상태를 파생 계산하면 상태 필터 조건이 함수식이 되어 인덱스를 못 타고(S-40) 풀 스캔이 된다
- 어긋나는 데이터
  - 화면의 상태와 실제 출입 판정 결과가 어긋난다 (목록엔 유효인데 출입은 거부)

### S-36

> 회원 한 명의 출입 이력과 회원권 변경 이력

- 명시되지 않은 것
  - "변경 이력"의 범위 (등록 · 정지 · 연장 · 차감 · 만료 중 무엇을 남기는지)
  - 이력의 기록 방식 (이벤트 로그인지 스냅샷인지)
  - 조회 기간 필터 · 페이지네이션 · 정렬 순서
  - 타 지점에서 등록된 이력도 보이는지 (지점 격리와의 관계)
- 깨지는 시나리오

## 3. 숨은 요구사항

### H-1. 모든 API에서 지점 격리를 일관되게 강제해야 한다

- 왜 필요한가: 한 API라도 지점 검증이 빠지면 헤더 변조만으로 타 지점 데이터가 노출·오염된다
- 유도된 문장: S-10 · S-4

### H-2. 같은 회원의 동시 출입 요청에서도 차감이 정확히 1회만 일어나야 한다

- 왜 필요한가: "오늘 차감했는가" 검사와 차감 사이 경쟁 조건이 있으면 이중 차감된다. 검증 요구가 이 시나리오를 명시한다
- 유도된 문장: S-22 · S-23 · S-37

### H-3. 유효 회원권 1개 제약이 동시 등록 요청에서도 지켜져야 한다

- 왜 필요한가: 애플리케이션 검사만으로는 검사-삽입 틈으로 2건이 들어온다. DB 수준 보강 또는 잠금이 필요하다
- 유도된 문장: S-18

### H-4. 출입 기록과 횟수 차감은 원자적으로 함께 성공하거나 함께 실패해야 한다

- 왜 필요한가: 둘 중 하나만 반영되면 출입 이력 건수와 잔여 횟수가 영구히 어긋난다
- 유도된 문장: S-20 · S-22 · S-36

### H-5. 어떤 회원권에 어떤 안내를 보냈는지 발송 이력을 기록해야 한다

- 왜 필요한가: 기록이 없으면 재실행 · 재시도 시 중복 발송을 막을 수 없고, 재시도 대상 자체를 찾을 수 없다
- 유도된 문장: S-29 · S-30 · S-32

### H-6. 배치가 실패·중단 후 재실행되어도 이미 발송된 건은 다시 보내지 않아야 한다

- 왜 필요한가: 09:00 실행 중 프로세스가 죽으면 재실행이 필요한데, 멱등하지 않으면 앞부분 대상에게 이중 발송된다
- 유도된 문장: S-29 · S-31 · S-32

### H-7. 발송 실패 건은 시도 횟수와 함께 남겨 상한 판정이 가능해야 한다

- 왜 필요한가: 시도 횟수를 모르면 재시도 상한(직접 정의)을 적용할 수 없다
- 유도된 문장: S-32 · S-33

### H-8. 외부 발송 지연이 대상 건수에 비례해 배치 시간을 무한정 늘리지 않아야 한다

- 왜 필요한가: 건당 100~500ms 직렬 발송은 10만 회원 규모에서 배치가 수 시간을 넘겨 다음 실행과 겹칠 수 있다
- 유도된 문장: S-4 · S-14 · S-31

### H-9. 날짜 계산(개월 더하기 · 정지 일수 더하기)은 월말 · 2월 · 윤년에서 결정적 규칙을 가져야 한다

- 왜 필요한가: 규칙 없이는 파라미터 테스트(S-38)의 기대값을 정할 수 없고 구현마다 종료일이 달라진다
- 유도된 문장: S-17 · S-25 · S-38

### H-10. 회원권 상태(유효 · 정지 · 만료)는 시간 경과를 즉시 반영해 일관되게 판정되어야 한다

- 왜 필요한가: 자정 경과 시 목록의 상태와 출입 판정 결과가 어긋나면 안 된다
- 유도된 문장: S-21 · S-28 · S-35

### H-11. 만료 · 소진된 회원권에는 출입 · 정지 · 차감 이벤트가 거부되어야 한다

- 왜 필요한가: 종료된 대상에 정지(연장)를 허용하면 만료를 되살릴 수 있고, 잔여 0회 차감은 음수를 만든다
- 유도된 문장: S-21 · S-24 · S-25

### H-12. 회원권의 등록 · 정지 · 연장 · 차감이 변경 이력으로 남아야 한다

- 왜 필요한가: 현재 상태만 저장하면 회원권 변경 이력 조회(S-36)를 만들 수 없다
- 유도된 문장: S-36 · S-24 · S-25

### H-13. 잘못된 입력 · 없는 리소스 · 규칙 위반은 4xx로 응답하고 500으로 새지 않아야 한다

- 왜 필요한가: 없는 회원 ID · 음수 횟수 · 누락된 지점 헤더가 500이면 클라이언트가 원인을 구분할 수 없다
- 유도된 문장: S-10 · S-16 · S-17 · S-21

### H-14. 하루에 같은 회원권이 여러 안내 조건에 걸려도 대상 선정이 모순 없이 동작해야 한다

- 왜 필요한가: 대상 추출 쿼리 결과에 같은 회원권이 중복으로 실리면 같은 시각에 안내가 2건 나간다
- 유도된 문장: S-29 · S-30

### H-15. 10만 규모 전제에서 목록 · 이력 조회는 인덱스를 타는 조건과 페이지 단위 응답이어야 한다

- 왜 필요한가: 전체 반환 · 풀 스캔은 규모 전제(S-4)와 실행 계획 검증(S-40)을 충족할 수 없다
- 유도된 문장: S-4 · S-34 · S-35 · S-36 · S-40

### 관점별 확인

1. 같은 요청이 두 번 들어오는 경우 → H-2 (출입) · H-3 (회원권 등록). 회원 등록 중복은 C-18 (범위 결정)
2. 외부 시스템 응답이 늦거나, 두 번 오거나, 순서가 바뀌는 경우 → H-5 · H-7 · H-8. 응답이 두 번 오는 경우는 해당 없음 (S-13 인터페이스가 동기 단일 응답)
3. 처리 중 프로세스가 죽는 경우 → H-6 (배치 재실행 멱등성) · H-4 (출입-차감 원자성)
4. 두 인스턴스가 같은 데이터를 동시에 집는 경우 → H-2 · H-3. 배치 중복 실행은 H-6과 C-13
5. 시간 경계 (월말 · 2월 · 자정 · 금지 시간대 직전 등) → H-9 (월말 · 2월) · H-10 (자정 상태 전이) · C-5 (하루 경계)
6. 데이터가 없거나 0인 경우 → H-11 (잔여 0회) · H-13 (없는 리소스). 안내 대상 0건인 날은 해당 없음 (빈 배치 실행은 부작용이 없음)
7. 이미 종료된 상태의 대상에 다시 이벤트가 오는 경우 → H-11
8. 입력 목록 안에 같은 항목이 중복된 경우 → H-14 (배치가 뽑은 대상 목록의 중복). 사용자 입력에 목록형 파라미터는 원문에 없음
9. 잘못된 입력이 서버 오류(500)로 새는 경우 → H-13

## 4. 결정이 필요한 항목

### C-1. 회원권 상태(유효 · 정지 · 만료)를 컬럼으로 저장할지 날짜에서 파생 계산할지

- 관련: S-35 · S-21 · H-10 · S-40
- 선택지
  1. 상태 컬럼 저장 + 전이 시점에 갱신
     - 장점: 상태 필터가 단순 등호 조건이라 인덱스를 태우기 쉽다
     - 단점: 자정 경과 등 시간에 의한 전이를 갱신 배치 없이는 반영하지 못해 조회와 실제가 어긋날 수 있다
  2. 종료일 · 정지 기간 · 잔여 횟수에서 매 조회 시 파생 계산
     - 장점: 시간 경과가 즉시 반영되어 갱신 누락이 없다
     - 단점: 필터 조건이 복합식이 되어 인덱스 설계(S-40)가 어려워진다
  3. 저장 + 조회 시 날짜 조건 병행 (저장 상태는 근사, 판정은 날짜로 보정)
     - 장점: 인덱스 활용과 정확성을 절충한다
     - 단점: 상태의 진실 원천이 둘이 되어 규칙이 복잡해진다

### C-2. 정지 가능 횟수 · 기간 상한의 수치와 적용 범위

- 관련: S-26 · S-27 · S-38
- 선택지
  1. 회원권당 누적 상한 (예: 최대 N회 · 누적 M일)
     - 장점: 판정에 회원권 데이터만 필요해 단순하다
     - 단점: 장기 회원권일수록 상대적으로 정지 여유가 부족해진다
  2. 회원권 기간에 비례한 상한 (예: 개월당 M일)
     - 장점: 기간에 공평하다
     - 단점: 계산 규칙이 늘고 횟수제에는 적용 기준이 따로 필요하다
  - 수치 자체(N회 · M일 · 1회 최소/최대 일수)도 함께 확정해야 한다

### C-3. 발송 재시도의 상한 · 시점 · 간격

- 관련: S-32 · S-33 · H-7 · S-14
- 선택지
  1. 실패 즉시 인라인 N회 재시도
     - 장점: 구현이 단순하고 같은 배치 안에서 종결된다
     - 단점: 지연 100~500ms × 재시도만큼 배치가 길어지고, 일시 장애면 연속 실패한다
  2. 실패 건을 기록해 두고 별도 주기(또는 다음 09:00 배치)에 재시도
     - 장점: 배치 시간이 안정적이고 프로세스 중단에도 재시도 대상이 남는다
     - 단점: 발송 상태 저장 · 재시도 스케줄 구현이 추가된다
  - 상한 횟수 수치도 함께 확정해야 한다

### C-4. "만료 7일 전"의 대상 선정 조건

- 관련: S-29 · S-39 · H-5
- 선택지
  1. 종료일 - 7일 == 오늘, 종료일 == 오늘인 건만 (정확히 두 날)
     - 장점: 하루 1건씩만 뽑혀 중복 발송 걱정이 적다
     - 단점: 배치가 하루 실패하면 그날 경계의 대상이 영구 누락된다
  2. 종료일이 오늘~7일 이내 전부, 발송 이력으로 중복 제거
     - 장점: 배치 실패 다음 날 자동으로 누락분이 복구된다
     - 단점: 발송 이력 조회가 대상 선정 쿼리에 끼어 복잡해진다

### C-5. "하루 1회"의 하루 경계와 타임존

- 관련: S-23 · S-37 · H-2
- 선택지
  1. 서버 기준 KST 달력일 자정 경계
     - 장점: 규칙이 단순하고 쿼리로 판정하기 쉽다
     - 단점: 자정 전후 방문이 2회로 차감된다 (심야 운영 시)
  2. 마지막 차감 시각으로부터 N시간 경과 기준
     - 장점: 자정 직전 방문의 이중 차감이 없다
     - 단점: "하루"라는 원문 표현과 어긋날 수 있고 판정 로직이 복잡하다

### C-6. 기간제 종료일 계산 규칙 (월 단위 더하기 · 종료일 포함 여부)

- 관련: S-17 · S-38 · H-9
- 선택지
  1. 달력 개월 더하기(1/31+1개월=2/28)에 종료일 당일 이용 가능
     - 장점: 표준 라이브러리(`plusMonths`) 동작과 일치해 검증이 쉽다
     - 단점: 월말 시작 회원권의 이용 일수가 월에 따라 달라진다
  2. 개월을 30일 등 고정 일수로 환산
     - 장점: 모든 회원권의 이용 일수가 같다
     - 단점: "기간(개월)"이라는 원문 단위와 어긋나는 해석이 된다
  - 종료일 당일 포함/미포함도 함께 확정해야 한다

### C-7. 횟수제 회원권의 만료 개념

- 관련: S-17 · S-29 · S-30 · S-35
- 선택지
  1. 횟수제에도 유효기간(종료일)을 부여 (시작일 + 가정한 기간)
     - 장점: 만료 안내 · 만료 임박 정렬 · 만료 상태를 기간제와 같은 축으로 다룬다
     - 단점: 원문에 없는 기간을 가정으로 추가해야 한다
  2. 횟수제는 잔여 0회 소진만 종료 사유로 두고 종료일 없음
     - 장점: 원문에 적힌 입력 항목(시작일 · 횟수)만으로 성립한다
     - 단점: 만료 임박 정렬에서 횟수제의 정렬 키가 없고, 만료 7일 전 안내가 적용 불가하다

### C-8. 정지 요청의 파라미터와 규칙

- 관련: S-24 · S-25 · S-26 · H-11
- 선택지
  1. 시작일 + 일수(또는 종료일)로 예약 정지, 조기 해제 허용
     - 장점: 실제 운영 시나리오(휴가 예약 등)에 맞는다
     - 단점: 예약 · 해제 · 겹침 검사 등 상태 관리가 늘어난다
  2. 요청 즉시 시작하는 정지만 허용, 해제 시점에 실제 일수만큼 연장
     - 장점: 겹침 · 소급 문제가 원천 차단된다
     - 단점: 미래 정지를 예약할 수 없어 기능이 좁아진다
  - 횟수제의 정지 허용 여부도 함께 확정해야 한다 (C-7과 연동)

### C-9. "연장"의 범위 해석

- 관련: S-25 · S-38
- 선택지
  1. 정지에 따른 자동 연장만 존재 (별도 연장 API 없음)

     - 단점: 검증 요구의 "정지·연장"(S-38)을 별개 기능 2개로 읽는 해석과 어긋날 수 있다
  2. 운영자가 종료일을 늘리는 별도 연장 기능도 포함
     - 장점: "정지·연장"을 병렬 기능으로 읽는 해석을 충족한다
     - 단점: 원문에 근거 문장이 없는 기능을 추가하게 된다

### C-10. 지점 헤더 형식과 회원 · 회원권의 지점 귀속 모델

     - 단점: 타 지점 이용(전 지점 공통권) 같은 확장을 막는 구조가 된다
  2. 회원권 · 출입 기록이 각각 지점을 가짐 (회원은 전사 공유)

     - 단점: "다른 지점 데이터 거부"의 판정 지점이 API마다 달라진다
  - 헤더 이름과 값 형식, 헤더 누락 · 미존재 지점의 응답 코드도 함께 확정해야 한다

### C-11. 출입 API의 중복 요청 처리와 두 번째 이후 출입의 응답

- 관련: S-20 · S-23 · S-37 · H-2

     - 단점: 동시 요청 테스트의 기대 응답(모두 성공)이 이중 차감 여부를 응답만으로 못 가린다
  2. 하루 두 번째 이후는 별도 코드(또는 차감 여부 필드)로 구분해 응답
     - 장점: 클라이언트와 테스트가 차감 발생 여부를 판별할 수 있다
     - 단점: 응답 규약이 늘어난다

### C-12. 목록 · 이력 API의 페이지네이션 방식과 식별자 형식

     - 단점: 정렬 키가 바뀌는 필터 조합마다 커서 규약을 설계해야 한다

### C-13. 안내 발송의 중복 방지 단위와 배치 중복 실행 대책

     - 단점: 발송 이력 테이블과 종류 체계를 설계해야 한다
  2. 배치 시작 시 잠금(또는 단일 인스턴스 전제)으로 실행 자체를 1회로 제한

### C-14. 잔여 3회 안내의 정확한 트리거

- 관련: S-30 · S-39 · H-14
- 선택지
  1. 09:00 배치에서 "잔여 == 3"이고 아직 안내 안 한 회원권
     - 장점: 만료 안내와 같은 배치 축으로 묶인다
     - 단점: 3을 건너뛰어 2가 된 회원권은 대상에서 빠진다
  2. 09:00 배치에서 "잔여 <= 3"이고 이 회원권에 잔여 안내를 보낸 적 없음
     - 장점: 건너뛴 경우도 포착된다
     - 단점: "잔여 3회일 때"라는 원문 문구보다 넓은 해석이다
  3. 차감으로 3회 도달한 즉시 발송 (배치 아님)
     - 장점: 안내가 가장 빠르다
     - 단점: 출입 트랜잭션에 외부 호출(100~500ms)이 끼고, "매일 09:00 자동 실행"(S-31)과의 관계 해석이 필요하다

### C-15. 유효 회원권 1개 제약의 판정 범위

- 관련: S-18 · H-3 · C-1
- 선택지
  1. 오늘 기준 유효한 회원권이 있으면 신규 등록 거부, 미래 시작도 기간이 겹치면 거부
     - 장점: 어떤 시점에도 겹침이 없어 "같은 시점에 하나"가 엄밀히 지켜진다
     - 단점: 만료 직전 미리 재등록(연속 이용)하려면 겹침 판정 로직이 필요하다
  2. 현재 유효한 것이 없으면 등록 허용 (미래 겹침은 검사하지 않음)
     - 장점: 판정이 단순하다
     - 단점: 미래 시작 회원권 2개가 겹치게 등록될 수 있다

### C-16. 정지 중 · 만료 임박 조건이 겹칠 때의 안내 우선순위

     - 단점: 정지 해제 시 종료일이 밀리면 이미 보낸 안내의 날짜가 틀린 정보가 된다
  2. 정지 중 회원권은 안내 대상에서 제외, 해제 후 새 종료일 기준으로 재판정
     - 장점: 안내 내용이 항상 최종 종료일과 일치한다
     - 단점: 대상 선정에 정지 상태 조건이 추가되고, 해제 시점에 따라 7일 전 안내가 생략될 수 있다

### C-21. (설계 재점검 후 추가) 날짜 경과에 따른 상태 보정 방식

     - 장점: 목록 필터가 등호 조건 그대로이고 예약 정지 전이도 함께 해결된다

  3. 배치 + 조회 보정 병행
     - 장점: 가장 정확하다
     - 단점: 구현량과 설명할 거리가 가장 많다

### C-22. (설계 재점검 후 추가) 미래 시작 회원권과 현재 회원권의 겹침

     - 장점: 미리 재등록이 가능하다

### C-24. (설계 재점검 후 추가) 정지 상한의 계산 기준

- 선택지
  1. 도메인에서도 `COMMON_INVALID_INPUT`(400)을 던진다
     - 장점: 에러 코드가 늘지 않는다
     - 단점: 어느 도메인의 입력 오류인지 코드로 구분되지 않는다
  2. `MEMBER_INVALID_INPUT` · `MEMBERSHIP_INVALID_INPUT`(400) 전용 코드를 추가한다
     - 장점: 도메인별로 코드가 뚜렷하다
     - 단점: 문서 · ErrorCode · TC를 더 고쳐야 한다

## 5. 평가자 관점

### 5.1 검증 요구가 확인하려는 역량

1. 동시 요청에서의 정합성 제어 (잠금 · 유니크 제약 · 트랜잭션 경계 선택) — 근거: S-37
2. 날짜 · 달력 경계 로직을 규칙으로 정의하고 파라미터 테스트로 증명하는 능력 — 근거: S-38
3. 배치 대상 선정 쿼리의 경계 조건(부등호 · 당일 포함)을 테스트로 고정하는 능력 — 근거: S-39
4. 데이터 규모를 전제로 한 인덱스 설계와 실행 계획으로 근거를 대는 능력 — 근거: S-40 · S-4
5. 모호한 요구를 스스로 가정하고 근거를 문서화하는 능력 — 근거: S-12 · S-42
6. 제한 시간에서 범위를 판단하고 미구현을 방향으로 정리하는 능력 — 근거: S-5 · S-6 · S-42

### 5.2 평가 비중이 클 것 같은 순서

1. 동시 출입에서의 하루 1회 차감 정합성
   - 이유: 검증 요구 첫 항목(S-37)이고, 출입-차감(S-22 · S-23)이 도메인의 핵심 규칙이다
2. 핵심 흐름의 동작 (회원 · 회원권 등록 → 출입 → 조회)
   - 이유: 이것이 없으면 검증 요구 자체를 시연할 수 없다 (S-16~S-23 · S-34~S-36)
3. 날짜 계산 · 안내 대상 선정의 경계 테스트
   - 이유: 검증 요구 4개 중 2개(S-38 · S-39)가 경계 케이스를 명시적으로 지목한다
4. 가정과 근거의 문서화
   - 이유: "직접 정의"가 원문에 3번(S-12 · S-27 · S-33) 나오고 README 항목(S-42)으로도 요구된다
5. 목록 조회 인덱스 설계 근거와 실행 계획
   - 이유: 검증 요구(S-40)이지만 코드 동작보다 문서 · 증빙 성격이라 대체 수단이 있다
6. 만료 안내 배치와 재시도 (확인 필요)
   - 이유: 필수 요구사항이지만 검증 요구에서 "대상 선정"만 지목되어, 발송 파이프라인 자체의 비중은 추론이다

### 5.3 제한 시간(3시간) 안에 다 못 할 때

**포기하면 감점이 큰 것**
1. 동시 출입 테스트와 그것이 통과하는 차감 구현 (S-37 — 검증 요구 정면)
2. 지점 헤더 식별과 타 지점 접근 거부 (S-10 — 기술 조건으로 명시)
3. 회원 · 회원권 등록과 출입의 기본 흐름 (S-16~S-23 — 다른 모든 것의 전제)
4. 날짜 계산 파라미터 테스트 (S-38 — 월말 · 2월이 명시적 지목)
5. Docker Compose 실행 (S-8 — 실행이 안 되면 평가 자체가 막힘)
6. README의 가정 · 미구현 항목 정리 (S-42 · S-6 — 미구현이어도 방향 기재로 평가받는 통로)

**설계안으로 대체해도 되는 것**
1. 발송 재시도의 실제 스케줄 구현 (상한 · 방식을 README에 정의하고 기록 구조만 구현)
2. 실행 계획 증빙의 대량 데이터 재현 (인덱스 설계 근거 서술 + EXPLAIN 첨부로 대체)
3. 회원권 종류 확장 구조의 완전한 일반화 (확장 지점 설명으로 대체)
4. 배치 다중 인스턴스 중복 실행 방지 (단일 인스턴스 전제를 명시하고 방안 서술)
5. 페이지네이션 최적화 (기본 방식 구현 + 한계와 개선안 서술)
