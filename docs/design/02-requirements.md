# 요구사항 구체화

> 아래 두 문서를 구현 가능한 단위로 쪼갠다.
> - 과제 원문: [00-assignment.md](00-assignment.md)
> - 분석: [01-analysis.md](01-analysis.md)
>
> 이 문서가 **요구사항 ID와 테스트 케이스 ID의 유일한 출처**다.

## ID 규칙

| 접두 | 뜻 | 형식 | 예 |
|---|---|---|---|
| `FR` | 기능 요구사항 | `FR-{F}.{항}` | `FR-2.1` |
| `NFR` | 비기능 요구사항 (동시성·정합성·기술 조건) | `NFR-{항}` | `NFR-3` |
| `SUB` | 제출물 요구사항 | `SUB-{항}` | `SUB-2` |
| `D` | 모호한 점에 대한 결정 | `D-{항}` | `D-4` |
| `TC` | 테스트 케이스 | `TC-{F}-{번호}` | `TC-2-07` |

- ID는 재사용하지 않는다. 삭제하면 번호를 비워 둔다
- `{F}`는 `task_list`의 기능(F) 번호와 같다
  - F1 기초 설정은 `FR`이 없고 `TC-1-xx`만 있다 (값 객체 · 공통 검증)
  - 첫 도메인 기능은 F2 → `FR-2.x` · `TC-2-xx`
- 원문 한 문장 = 요구사항 한 행
  - 한 문장에 규칙이 둘이면 행을 나눈다
- 원문에 없는데 필요해서 추가한 요구사항
  - `원문` 열에 `(파생 H-n)`이라 적는다
  - 필요하면 `D`로 근거를 남긴다
- 분석 문서의 ID를 출처로 쓴다
  - `S-n` 원문 문장
  - `H-n` 숨은 요구사항
  - `C-n` 결정 항목 → 사용자가 정하면 §5 `D-n`

**범위 밖** (구현하지 않는다 — 면접에서 물어보면 여기가 근거)

- 별도 연장 API (D-9 · D-18) — 연장은 정지에 따른 자동 연장만 구현
- 환불 금액 계산 · 결제 연동 (D-18) — 결제 금액은 저장만 한다
- H-8: 발송 병렬화 · 배치 시간 상한 — 3시간 범위에서 직렬 발송 전제
  - 대상 건수 증가 시의 개선 방향은 README에 기재
- 만료 전 미리 재등록 (D-15 · C-22의 한계) — README에 한계 기재
  - 종료일 ≥ 오늘인 회원권이 있으면 미래 시작 등록도 거부된다
  - 미래 시작 회원권끼리의 겹침도 같은 규칙으로 차단된다
- 09:00 당일 안내를 놓친 날의 보충 발송 (D-4의 한계) — README에 한계 기재
- 배치 다중 인스턴스 중복 실행 방지 — 단일 인스턴스 전제
  - 안내 배치는 발송 이력 유일 키(D-13)가 방어한다
  - 상태 동기화 배치는 멱등 UPDATE(D-21)라 두 번 돌아도 결과가 같다

### F2. 회원 · 회원권 등록

| ID | 원문 | 구체화 (구현 기준) | 구분 |
|---|---|---|---|
| FR-2.1 | S-16 | 이름 · 연락처를 받아 회원을 등록한다 | 필수 |
| FR-2.2 | S-17 | 회원 · 종류 · 시작일 · 기간(개월) 또는 횟수 · 결제 금액으로 회원권을 등록한다 | 필수 |
| FR-2.3 | S-18 | 종료일 ≥ 오늘인 `ACTIVE` · `PAUSED` 회원권이 있는 회원의 신규 등록을 거부한다 | 필수 |
| FR-2.4 | S-19 | 회원권 종류(기간제 · 횟수제)를 추가할 수 있는 구조로 만든다 | 필수 |

**상세 정책**

- 기간제 종료일 = `시작일.plusMonths(개월)` (D-6)
  - 예: 1/31 + 1개월 = 2/28 (윤년이면 2/29)
  - 종료일 당일까지 이용 가능 (포함)
- 횟수제 종료일 = `시작일.plusMonths(6)` (D-7, 가정 — README에 근거 기재)
  - 6개월은 `MembershipType` enum 상수다 (D-7 보충, C-32)
- 개월 수를 `membership.months`에 저장한다 (D-24)
  - 기간제 = 요청 개월, 횟수제 = 6
  - 정지 누적 상한(개월 수 × 7일, D-2)이 이 값을 쓴다
- 등록 거부 조건 (D-15 · D-19, C-22로 범위 확대)
  - 상태 `ACTIVE` · `PAUSED` **그리고** 종료일 ≥ 오늘인 회원권이 있으면 거부한다
  - 정지 중(`PAUSED`)도 포함한다 (D-19, TC-2-09)
  - 시작일이 미래인 회원권도 포함한다 (C-22, TC-2-11)
    - 겹침 경로가 모두 막혀 출입 판정 대상이 항상 1건 이하가 된다
  - 종료일 < 오늘인 stale `ACTIVE` · `PAUSED`는 세지 않는다 (TC-2-10)
    - 상태 동기화 배치(D-21)가 돌기 전이어도 재등록이 가능하다
  - 한계: 만료 전 미리 재등록할 수 없다 (§1 범위 밖, README 기재)
- 동시 등록은 DB 수준에서 방어한다 (NFR-3, 방식은 [03 §7](03-domain-model.md))
- 입력 검증 (H-13 파생, README 가정)
  - 기간(개월) · 횟수는 1 이상
  - 결제 금액은 0 이상
  - 시작일 값 자체는 제한하지 않는다 (원문에 제한 없음)
- 등록 입력 규칙 (D-23) — 위반은 모두 도메인에서 `MEMBERSHIP_INVALID_INPUT` 400
  - 개월 ≤ 120
  - 횟수 ≤ 1000
  - 계산된 종료일 ≤ 9999-12-31 (TC-2-15)
  - 기간제에 `count`가 오면 거부한다 (TC-2-16)
  - 횟수제에 `months`가 오면 거부한다 (TC-2-16)
  - 상한 수치 120 · 1000은 가정이다 — README에 기재
  - 목적: 극단 입력이 `DateTimeException` · MySQL DATE 범위 초과로 500이 되는 경로를 막는다 (NFR-8)
- FR-2.4는 구조 요구라 TC 대신 [03 도메인 모델](03-domain-model.md)의 종류별 분리 설계로 검증한다

### F3. 출입

| ID | 원문 | 구체화 (구현 기준) | 구분 |
|---|---|---|---|
| FR-3.1 | S-20 | 회원 출입을 서버 시각으로 기록한다 | 필수 |
| FR-3.2 | S-21 | 요청 시점에 유효한 회원권이 있어야 출입을 허용한다 | 필수 |
| FR-3.3 | S-22 | 횟수제는 출입 시 잔여 횟수를 1회 차감한다 | 필수 |
| FR-3.4 | S-23 | 같은 달력일(KST)의 두 번째 이후 출입은 차감하지 않는다 | 필수 |

**상세 정책**

- 판정 대상 회원권 = 상태 `ACTIVE` · `PAUSED` 그리고 종료일 ≥ 오늘
  - 등록 규칙(C-22)으로 항상 1건 이하다 ([03 §7](03-domain-model.md))
- 유효 판정 (요청 처리 시각 기준)
  - 시작일 ≤ 오늘 ≤ 종료일 (양끝 포함, D-6)
  - 오늘이 정지 구간 밖 (FR-4.4)
    - 조기 해제한 정지는 해제 당일까지 정지 구간이다 (C-23 → D-8)
  - 횟수제는 잔여 ≥ 1 (H-11)
  - 저장 상태가 아니라 날짜 · 정지 구간 · 잔여로 판정한다 (H-10)
- 하루 = 서버 KST 달력일, 자정 경계 (D-5)
- 두 번째 이후 출입도 동일한 성공 응답, 기록은 남기고 차감만 생략 (D-11)
- 거부된 출입 시도는 기록하지 않는다 (원문에 요구 없음)
- 출입 기록과 차감은 한 트랜잭션이다 (NFR-4)
- 동시 요청 제어 방식은 [03 §7](03-domain-model.md)에서 정한다 (NFR-2)

### F4. 정지와 연장

| ID | 원문 | 구체화 (구현 기준) | 구분 |
|---|---|---|---|
| FR-4.1 | S-24 | 시작일 + 일수로 회원권 정지를 등록한다 (예약 가능, 조기 해제 가능) | 필수 |
| FR-4.2 | S-25 | 실제 정지 일수(조기 해제 시 해제 당일까지)만큼 종료일을 연장한다 | 필수 |
| FR-4.3 | S-26 · S-27 | 정지 횟수 · 누적 일수 상한을 검사해 초과를 거부한다 | 필수 |
| FR-4.4 | S-28 | 정지 기간(조기 해제 당일 포함) 중의 출입을 거부한다 | 필수 |

**상세 정책**

- 상한 수치 (D-2)
  - 정지 횟수: 회원권당 최대 3회
  - 누적 정지 일수: 개월 수 × 7일 (횟수제는 6개월 기준 42일, D-7)
    - 개월 수는 `membership.months` 컬럼 값이다 (D-24)
  - 1회 최소 1일
- 상한 계산 기준 (C-24 → D-2)
  - 정지 횟수: 시작 전 해제(사용 0일)한 정지는 세지 않는다 (TC-4-13)
  - 누적 일수: 해제된 건은 사용 일수로 센다
  - 누적 일수: 해제되지 않은 건(예약 · 진행 중)은 예정 일수로 센다
- 정지 기간은 시작일 · 종료일 당일 포함
  - 정지 종료일 = 시작일 + 일수 − 1
  - 정지 시작일 당일부터 출입 거부
- 연장 규칙 (D-8, S-25의 "정지 기간만큼" = 실제 정지 일수)
  - 등록 시 예정 일수만큼 종료일 즉시 연장
  - 조기 해제 시 미사용 일수만큼 종료일을 되돌린다
  - 사용 일수 = 정지 시작일 ~ 해제 당일 (양끝 포함, TC-4-07)
    - 정지 시작 전 해제는 사용 0일
- 조기 해제 당일까지 정지로 계산한다 (C-23 → D-8)
  - 해제 당일 출입은 거부한다 (`ATTENDANCE_MEMBERSHIP_PAUSED`, TC-4-12)
  - 출입은 해제 다음 날부터 가능하다
- 정지 시작일은 오늘 이후만 허용한다 (예약 정지 결정의 함의, 소급 근거 없음)
- 상태 전이 ([03 §4](03-domain-model.md))
  - 시작일 = 오늘인 정지를 등록하면 즉시 `PAUSED`
  - 미래 시작 정지는 `ACTIVE` 유지, 시작일 00:00 상태 동기화 배치가 `PAUSED`로 바꾼다 (D-21)
  - 해제 후, 해제 대상을 제외하고 오늘을 포함하는 정지가 남으면 `PAUSED` 유지, 없으면 `ACTIVE`
- 정지 중(`PAUSED`)에도 추가 예약 정지를 등록할 수 있다 (D-19)
  - 조건: 기존 정지와 기간 비겹침 + 상한 검사 통과
- 기간이 겹치는 정지 등록은 거부한다 (이중 연장 방지)
- 만료 · 취소된 회원권은 정지할 수 없다 (H-11)
  - 만료 판정 = 상태 `EXPIRED` 또는 종료일 < 오늘 (배치 전 stale 상태 방어, D-21)
- 정지 · 해제 · 연장은 회원권 변경 이력으로 남긴다 (FR-5.5)
- 횟수제도 동일 규칙으로 정지 가능 (D-8)

**상세 정책**

- 상태는 저장 컬럼이다 (D-1) — 값과 전이는 [03](03-domain-model.md)에서 정의
- 상태 동기화 배치 (D-21 · FR-5.6)
  - 매일 00:00(KST) 자동 실행
  - 종료일 < 오늘인 `ACTIVE` · `PAUSED` → `EXPIRED`
  - 어제로 끝난 정지만 있는(오늘을 포함하는 정지가 없는) `PAUSED` → `ACTIVE`
  - 오늘 시작하는 예약 정지가 있는 `ACTIVE` → `PAUSED`
  - 현재 상태를 조건에 넣은 bulk UPDATE라 다시 실행해도 결과가 같다 (멱등, TC-5-09)
  - 배치 전이는 변경 이력을 남기지 않는다 (FR-5.5의 이벤트가 아니다)
- 목록 조회 날짜 보정 (D-21) — 배치가 실패한 날의 안전망
  - `ACTIVE` · `PAUSED` 필터 = 해당 상태 그리고 종료일 ≥ 오늘
  - `EXPIRED` 필터 = 상태 `EXPIRED`, 또는 상태 `ACTIVE` · `PAUSED` 그리고 종료일 < 오늘
  - 응답의 상태 값도 같은 규칙으로 보정한다 (TC-5-08)
  - 정지 시작 · 종료에 따른 `ACTIVE` ↔ `PAUSED`는 조회에서 보정하지 않는다 (배치 담당)
- 만료 임박 순 = 종료일 오름차순 (횟수제도 종료일이 있어 같은 축, D-7)
- 페이지네이션은 offset 기반 (`page` · `size`, D-12)
- 목록은 헤더 지점 소속 회원권만 반환한다 (NFR-1)
- 이력 조회도 헤더 지점에 귀속된 기록만 반환한다 (D-10, "다른 지점 데이터 거부")
  - 조회는 403이 아니라 타 지점 데이터 0건 필터 방식이다 (NFR-1)
- 이력은 최신순 정렬, 페이지네이션 동일 적용
- 목록 쿼리는 복합 인덱스를 타야 한다 (NFR-5, 설계는 [03](03-domain-model.md))

### D-1. 회원권 상태를 저장할지 파생 계산할지

- 선택지

  - B: 매 조회 시 파생 계산 — 즉시 반영 / 필터가 복합식이 되어 인덱스 곤란
  - C: 저장 + 날짜 조건 병행 — 절충 / 진실 원천이 둘
- **결정**: A (상태 컬럼 저장 + 전이 시점 갱신)
- **근거**: 상태 필터를 단순 등호 조건으로 만들어 인덱스 설계(S-40)에 유리
- 남는 한계

    - 매일 00:00 상태 동기화 배치 + 조회 시 날짜 보정으로 해소한다 (D-21)

### D-2. 정지 상한의 수치와 적용 범위

- 관련: C-2 · FR-4.3
- 원문: S-26 · S-27 "정지 가능 횟수와 기간에는 상한이 있음. 상한은 직접 정의"
- 선택지
  - A: 회원권당 고정 누적 상한 — 판정 단순 / 장기권에 상대적으로 불리
  - B: 기간 비례 상한 — 기간에 공평 / 계산 규칙 증가, 횟수제 기준 별도 필요
- **결정**: B — 개월당 누적 7일, 정지 횟수 회원권당 최대 3회, 1회 최소 1일
  - "개월 수 × 7일"의 개월 수는 `membership.months` 컬럼 값이다 (C-29 → D-24)
  - 계산 기준 보충 (C-24 — 설계 재점검 후 결정)
    - 시작 전 해제한 정지(사용 0일)는 횟수에서 제외한다
    - 누적 일수는 해제된 건은 사용 일수, 예약 · 진행 중인 건은 예정 일수로 센다
- **근거**: 기간에 공평한 방식. 수치는 어시스턴트 제안을 사용자가 수용
  - C-24: 분석 §7 기록 그대로 선택지 1
    - 선택지 1 장점: 일찍 해제한 만큼 상한이 돌아와 공정하다
    - 선택지 2(전부 횟수 · 예정 일수)는 단순하지만 일찍 해제해도 상한이 돌아오지 않는다
- 남는 한계
  - 횟수제 상한이 가정한 유효기간(D-7)에 의존한다
  - 상한 계산 규칙이 늘어난다 (C-24, TC-4-13)

### D-3. 발송 재시도의 상한 · 시점

    - 선택지 2: 설정 파일로 이동 — 규칙에 맞음 / 도메인까지 인자 증가

### D-19. "현재 유효"의 상태 범위와 정지 중 추가 예약

- 관련: C-19 · FR-2.3 · FR-4.1 · D-15 (설계 점검 M-1 · M-7 후 추가)
- 원문: S-18 · S-24
- 선택지
  - A: 유효 = ACTIVE + PAUSED — 정지 중 새 등록 거부, 추가 예약 정지는 겹침 없으면 허용 / 검사 조건 증가
  - B: 유효 = ACTIVE만 — 판정 단순 / 정지 중 새 등록이 허용돼 해제 시 겹침 위험
- **결정**: A — 유효 = `ACTIVE` + `PAUSED`
  - 정지 중(`PAUSED`) 회원의 새 회원권 등록은 거부한다 (TC-2-09)
  - `PAUSED` 상태의 추가 예약 정지는 기존 정지와 겹치지 않으면 허용한다 (상한 검사 포함)
  - 등록 거부의 날짜 조건은 종료일 ≥ 오늘이다 (C-22 → D-15)
- **근거**: 분석 §7 C-19 기록 그대로 — 정지 중 새 등록을 허용하면 해제 시 유효권 2개가 겹친다
- 남는 한계: 등록 거부 검사가 상태(`ACTIVE` · `PAUSED`) + 종료일 ≥ 오늘 병행 조건이 된다 (F2 상세 정책)

### D-21. 날짜 경과에 따른 상태 보정 방식

- 관련: C-21 · C-1 · D-1 · FR-5.2 · FR-5.6 (설계 재점검 N-1 후 추가)
- 원문: S-35 "상태(유효, 정지, 만료)별 필터, 만료 임박 순 정렬"
- 선택지
  - A: 매일 00:00 상태 동기화 배치 — 목록 필터가 등호 조건 그대로, 예약 정지 전이도 해결 / 배치 증가, 배치 실패 시 하루 어긋남
  - B: 조회 시 날짜 조건 보정 — 배치 없이 항상 정확 / OR 조건이라 인덱스 설명 복잡, 예약 정지 시작 전이는 따로 남음
  - C: 배치 + 조회 보정 병행 — 가장 정확 / 구현량 · 설명할 거리 최다
- **결정**: C — 매일 00:00 상태 동기화 배치 + 조회 시 날짜 보정 병행
  - 배치: 종료일 < 오늘인 `ACTIVE` · `PAUSED` → `EXPIRED`
  - 배치: 오늘 시작하는 예약 정지의 회원권 `ACTIVE` → `PAUSED`
  - 배치: 어제로 끝난 정지만 있는 회원권 `PAUSED` → `ACTIVE`
  - 배치는 멱등 bulk UPDATE다
  - 조회 보정: 종료일 < 오늘인 `ACTIVE` · `PAUSED`를 `EXPIRED`로 취급한다
- **근거**: 분석 §7 C-21 기록 그대로 선택지 3
  - 선택지 3 장점: 가장 정확하다
- 남는 한계
  - 배치 하나가 늘고 구현량이 가장 많다
  - `EXPIRED` 필터의 OR 조건은 실행 계획이 단순 등호보다 불리하다 ([03 §6](03-domain-model.md))
  - 조회 보정은 종료일 기준만 다룬다 — 정지 시작 · 종료 전이는 배치가 실패하면 하루 어긋난다
  - 배치 조건은 "오늘 시작 · 어제 종료" 문구를 유지한다 (C-26) — 배치가 빠진 날의 정지 전이는 다음 배치가 복구하지 못한다. 개선 방향("오늘을 포함하는 정지 유무"로 판정)은 README에 기재
  - 조기 해제 시 상태는 즉시 `ACTIVE`로 바꾼다 (C-25) — 해제 당일에는 목록 상태(`ACTIVE`)와 출입 결과(거부, D-8)가 어긋난다. README에 기재

### D-22. 도메인 입력 오류의 에러 코드

- 관련: C-27 · FR-2.1 · FR-2.2 · NFR-8 (F1 리뷰 후 추가)
- 원문: S-16 "회원 등록: 이름, 연락처" · S-17 "종류, 시작일, 기간(개월) 또는 횟수"
- 선택지
  - A: 도메인에서도 `COMMON_INVALID_INPUT` — 코드 증가 없음 / 도메인 구분 불가
  - B: 전용 코드 추가 — 도메인별 코드가 뚜렷함 / 문서 · 코드 · TC 추가 수정
- **결정**: B — `MEMBER_INVALID_INPUT` · `MEMBERSHIP_INVALID_INPUT` (400)
  - Request Bean Validation 실패는 그대로 `COMMON_INVALID_INPUT`이다
  - 도메인 생성 · 수정 검증 실패(VO 생성 실패 포함)는 전용 코드로 바꿔 던진다
  - `type`별 조건 필수(기간제 개월 · 횟수제 횟수) 위반은 `MEMBERSHIP_INVALID_INPUT`이다
- **근거**: VO의 `IllegalArgumentException`이 500으로 새지 않게 도메인에서 먼저 막는다 (NFR-8)
- 남는 한계: 같은 입력 오류라도 검증 위치(Request · 도메인)에 따라 코드가 다르다

### D-23. 회원권 등록 입력 규칙

- 관련: C-28 · C-30 · C-27 · FR-2.2 · NFR-8 (F2 리뷰 후 추가)
- 원문: S-17 "종류(기간제 또는 횟수제), 시작일, 기간(개월) 또는 횟수"
- 선택지 (C-28)
  - 1: 개월 ≤ 120 · 횟수 ≤ 1000 + 계산된 종료일 ≤ 9999-12-31 — 운영상 의미 없는 값까지 막음 / 상한 수치가 가정
  - 2: 계산된 종료일 범위만 검사 — 수치 가정 없음 / 600개월 같은 값이 통과
- 선택지 (C-30)
  - 1: 반대 종류 값이 오면 거부 — 의도가 불분명한 요청을 막음 / 클라이언트가 필드를 정확히 골라야 함
  - 2: 무시 — 관대함 / 0 · 음수면 Request 검증이 400을 내 "무시"와 어긋남
- **결정**: C-28 선택지 1 · C-30 선택지 1
  - 개월 ≤ 120, 횟수 ≤ 1000
  - 계산된 종료일이 9999-12-31을 넘으면 거부한다
  - 기간제에 `count`, 횟수제에 `months`가 오면 거부한다
  - 모두 도메인에서 `MEMBERSHIP_INVALID_INPUT` 400을 던진다
- **근거**: 분석 §7 기록 그대로
  - C-28: 개월 ≤ 120 · 횟수 ≤ 1000 + 계산된 종료일 ≤ 9999-12-31, 위반 시 `MEMBERSHIP_INVALID_INPUT`
  - C-30: 반대 종류 값이 오면 `MEMBERSHIP_INVALID_INPUT`
  - 극단 입력(시작일 9999-12-31 + 1개월 등)이 `DateTimeException` · MySQL DATE 범위 초과로 500이 되는 경로를 막는다 (NFR-8)
- 남는 한계
  - 120 · 1000은 가정이다 — README에 기재
  - 클라이언트가 종류에 맞는 필드만 골라 보내야 한다

### D-25. 애그리거트 간 논리 참조

- 관련: C-31 · C-10 · D-10 · FR-2.2 · FR-3.1 · FR-5.5 (F2 검증 후 추가)
